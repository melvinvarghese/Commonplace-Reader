# Foundation and Reader-Engine Proof Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a reproducibly buildable Android foundation and an offline reader proof that tests Readium EPUB plus both approved PDF candidates before selecting a PDF engine.

**Architecture:** Keep one application module, with Compose screens and ViewModels, a small application-owned dependency container, Room-backed durable records, app-private document copies, and separate EPUB/PDF integrations. The proof uses real persistence and lifecycle restoration, not in-memory notes or a universal rendering abstraction. Two temporary product flavors isolate PDF candidate dependencies while exercising the same fixtures and storage contracts.

**Tech Stack:** Kotlin, Compose/Material 3, ViewModel, coroutines/Flow, Room/KSP, DataStore, SAF, Readium Kotlin, AndroidX PDF and NucleusFramework/ComposePdfReader comparison builds, Gradle Kotlin DSL, JUnit, Android instrumentation, GitHub Actions.

**Spec:** [Approved architecture](../../ARCHITECTURE.md), committed at `62639d3`; read it together with this plan. Its approval/status wording describes the earlier review checkpoint: the owner has since approved drafting this plan, not implementation. The supplied `pasted_content.txt` is Android-development guidance rather than a separate product brief; no unstated product requirements are inferred from it.

## Global Constraints

- “Begin with one application module, organized by responsibility, not a collection of framework modules.”
- “Proposed baseline is Android 9/API 28 or newer, subject to the comparison.” API 28 is a proof target, not yet a public support promise.
- “Select and pin a compatible released dependency/toolchain set after review”; no dynamic versions, snapshots, or development-branch requirements treated as release requirements.
- “EPUB: Readium Kotlin.” “PDF: no final engine selected.” The exact PDF candidates are AndroidX PDF and `NucleusFramework/ComposePdfReader`.
- “Room is the canonical store.” “Missing precision stays missing.” “Human-facing physical page numbers are one-based.”
- “No accounts, default analytics, or internet dependency for core use.” No private writing, quotations, passwords, or private paths in logs.
- “No OCR is included.” “DRM support and circumvention are outside this beta.”
- “Existing history is preserved.” The owner selected Apache-2.0; the actual current LICENSE is GPL-3.0 and changes only during approved implementation.
- Original files remain untouched; exact duplicates open the existing source; removal/reattachment must never silently destroy writing or reuse incompatible coordinates.
- The architecture's accessibility, lifecycle, import-safety, backup-exclusion, and untrusted-input rules apply to this proof, not only to a later beta.

## Review Focus

1. SAF providers with unknown lengths, revoked access, or cancellation: leave no usable partial source and retain existing writing (Task 3).
2. Rotated/cropped pages, repeated passages, and multilingual text: selected text and persisted geometry must identify the same passage after zoom, reopen, and process death (Tasks 4–6).
3. Background/process death during a write or document switch: acknowledge only durable notes; restore the correct source, bookmark, and location (Tasks 2, 4–6).
4. Scans, encrypted/malformed files, fixed-layout EPUB, and hostile remote resources: return explicit capability/error states without crashes, invented selection, or remote fetches (Tasks 3–6).
5. Large documents and repeated open/close cycles on minimum/current Android and 16 KB systems: bounded resource use, no leaked sessions, and truthful per-device limitations (Tasks 5–7).

Tests use the same package layout as their subject. Keep flavor implementations separate, with no reflective engine discovery, new Gradle modules, DI framework, or common rendering superclass.

**Application value contracts:**

- `DocumentFormat { EPUB, PDF }`; `SourceAvailability { AVAILABLE, MISSING }`.
- `SourceEntity`: UUID string `id`, `title`, optional `authors`, `format`, `originalUri`, SHA-256 `checksum`, relative app-owned `assetPath`, `availability`, UTC epoch-millisecond `createdAt`/`modifiedAt`. Titles may fall back to sanitized provider display names; engine metadata extraction is not a separate subsystem.
- `SavedLocation(version: Int, format: DocumentFormat, engineId: String, payloadJson: String)`; version is `1`. Engine/version identity must be explicit and persisted, not inferred from file extension. Preserve complete Readium locator JSON.
- PDF JSON fields: `pageIndex` (zero-based physical), optional `pageLabel`, `pageBox` (four PDF-point bounds), `rotationDegrees`, optional selection `quads` (eight coordinates each) and `coordinateSpace = "unrotated-pdf-points"`. Preserve needed engine-native metadata alongside these fields; never derive geometry from character indices or screen pixels alone. If the candidate cannot map this space reliably, record a failed requirement, not fabricated precision.
- `Capture(quotation: String, location: SavedLocation)`; quotation is nonblank. `EntryEntity`: UUID `id`, `kind` (`HIGHLIGHT` or `ANNOTATION` for this proof), optional `sourceId`/`location`, title/body/quotation, attribution snapshot, optional ARGB highlight color, UTC creation/modification values. HIGHLIGHT requires nonblank quotation, attribution, and location; source-level ANNOTATION has body/attribution but no invented passage. Later entry types need a later schema/editor plan.
- `BookmarkEntity(id, sourceId, location, createdAt)` and `ReadingStateEntity(sourceId, location, modifiedAt)` are distinct records. Entry source FK uses `SET NULL` and retains attribution; book removal is not implemented here. Bookmark/progress FKs reference sources. Store location JSON as text via tested converters.
- `ReaderDraftEntity(sourceId, capture, reflection, colorArgb, modifiedAt)` is a separate Room draft, never a finished entry. `saveCapture` atomically inserts the entry and clears its draft. A source has one active capture draft in this proof; DataStore stores only reader preferences, not writing.
- `ReaderCapabilities` independently represents render, search, select, highlight display, and navigation as `Available`, `Unavailable(reason)`, or `Unknown`. Capabilities depend on the document, device, and candidate; unknown is not silently promoted to available.
- `ReaderEvent`: `Opened(capabilities)`, `PositionChanged(location)`, `SelectionChanged(captureOrNull)`, `Failed(userMessage)`; late events carry the source ID and are ignored after a source switch. These values are event/storage boundaries, not a universal renderer API.

## Shared PDF evidence protocol

Create READER_PROOF only when real experiments begin. Each row records candidate and artifact version, fixture hash, build commit, device/emulator model/API/extension level/ABI/page size, operation, expected result, observed result, pass/fail/not-run, and log/report reference. Emulator and physical-device evidence stay separate. Use the same corpus for both candidates; a feature missing on API 28 is not rescued by passing only on current Android.

For geometry, use reference quads from the fixture manifest and assert transforms round-trip within 1 PDF point and overlays align within 2 dp at the tested zoom levels (1× and 2×), crop/rotation and orientations. Record manual visual verification alongside numerical checks; screenshots alone do not establish durable coordinate correctness. Search and selection preserve exact Unicode text; any engine normalization difference is recorded and evaluated, not silently stripped to make the test pass.

For performance, use the same 2 GiB-RAM AVD profile for each candidate, identical cold/warm conditions and a 100 MiB fixture; sample `adb shell dumpsys meminfo <package>` before/open/after navigating 20 pages/after close for three cycles, plus Android profiler/StrictMode evidence where available. Proof acceptance budgets: first usable large-document page within 10 seconds, tested page navigation within 1 second after initial open, peak total PSS below 512 MiB, no ANR/OOM or main-thread file-copy/parsing violation, and post-close PSS not increasing by more than 32 MiB across the three cycles after the same idle/GC procedure. Record the procedure and raw measurements; these are reviewable proof thresholds, not a universal user-facing performance guarantee. Repeat relevant checks on a current device; budget failure triggers investigation or a rejected candidate, never hidden threshold changes.

Both candidates must demonstrate durable notes/bookmarks/progress/jump-back, explicit scan/no-text and encrypted/malformed behavior, resource cleanup on cancellation/open-close, offline operation, and accessible capture/navigation controls. Unsupported cases are valid explicit UX outcomes but do not satisfy mandatory text-PDF search/selection/highlighting. Unknown, unavailable hardware or unrun tests block an unqualified support claim.
